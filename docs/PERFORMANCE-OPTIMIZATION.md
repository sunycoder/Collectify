# Collectify 全项目性能优化方案

评估日期：2026-11-21。基于主程序 5.7.19 及当前工作区代码。

本方案是后续实施设计，不代表所有事项已经完成。上一轮性能修改仍在本地，尚未进入已发布的 5.7.19。Windows 数据不能替代 macOS 实机结果。

## 1. 目标与结论

目标是启动快、操作持续响应、后台安静、资源增长有上限，同时保留独立插件、热插拔、离线使用和签名校验。启动时间、内存与安全存在取舍，不以预加载所有插件换取切换速度，也不以取消校验换取首屏速度。

当前已有合理基础：独立插件包、页面沙箱、部分解析任务进程隔离、单实体增量写入、页面回收及按需加载编辑器。继续沿现有架构优化，暂不重写为其他桌面框架，不全面引入复杂状态框架，不把业务搬回宿主。

最高优先级是：补齐真实可操作指标 → 缩短启动依赖链 → 控制主进程工作量 → 优化大数据交互 → 建立持续性能门禁。

## 3. 测量方法与第一阶段目标

### 测试矩阵

- macOS 优先使用真实 Apple Silicon 设备，确认 arm64 安装包、Electron 主进程和计算任务架构；Intel 设备单独记录，避免混合统计。
- Windows、Linux 分别保留回归数据，不跨操作系统直接比较绝对时间。
- 区分首次安装、进程冷启动、同进程首次打开插件、已加载插件切换和长时间运行。系统重启后的首次运行单独记录，不能把“新进程”统一叫磁盘冷启动。
- 固定系统版本、CPU、内存、应用架构、供电模式、数据规模、插件组合和构建类型。正式安装包与开发模式分别报告。
- 每个稳定场景至少 30 个样本，报告 P50 / P95 / 最大值及失败数；首次授权、首次迁移、系统权限等待单列。

### 建议验收目标

下列为首轮工程目标，尚未达成。测完指定 Mac 基线后调整，并固定测试机器与数据集。

| 场景                                         | 初始目标                                                                  |
| -------------------------------------------- | ------------------------------------------------------------------------- |
| 普通启动至首插件可操作，默认五插件、常规数据 | P95 ≤ 2.5s；首次安装及首次授权单列                                        |
| 已安装全部官方插件后的启动                   | 相比默认组合，额外耗时 ≤ 300ms；未访问的重型可选插件不创建解析进程        |
| 轻量插件同进程首次打开                       | P95 ≤ 700ms                                                               |
| 已加载插件切换                               | P95 ≤ 150ms，并保留输入与滚动状态                                         |
| 输入、菜单和按钮反馈                         | P95 ≤ 100ms；加载状态在下一次可绘制帧呈现                                 |
| 普通操作中的主进程长任务                     | 优先消除由自有业务造成的连续 > 50ms 阻塞，保留诊断样本                    |
| 5000 条业务内容的关键词查询                  | P95 ≤ 300ms；新查询替代旧查询，不堆积结果                                 |
| 空闲 5 分钟                                  | 无网络操作和采集时，应用 CPU 以持续低占用为目标；记录唤醒频率，不写空数据 |
| 重复开关重型内容 30 轮                       | 任务、页面与资源数量回到预定边界，无持续上涨趋势                          |

内存首轮先建立“宿主 / 页面 / 后台 / 计算进程”分项基线，再分配预算。不能直接把各进程 Working Set 相加当作精确物理占用，也不为达成任意内存数字强行回收未保存内容。

### 必须新增的测量点

启动记录 imports、清单发现、签名验证、首次迁移、后台创建、窗口首次绘制、页面 DOM 就绪、插件业务数据就绪、首插件可操作。插件提供带本次加载标识的 ready 信号，宿主验证发送者；超时应显示失败，不能把 HTML 载入成功当作业务就绪。

常规诊断记录主进程事件循环延迟、CPU、进程与任务数量、读写次数及字节、缓存命中率、输入到结果呈现耗时。默认只存有界聚合数据，不记录用户正文、剪贴板内容、路径或凭据；详细 trace 由用户主动启动。

## 4. 启动与插件加载

### P0：按职责拆开插件发现、校验、准备和激活

现状：Registry 在启动时完整校验已安装原生插件；Services.load 会创建所有已安装后台以及部分保留数据插件的后台，之后才创建主窗口。后台暂未 activate 不等于后台 create 没有数据库和模块加载成本。

实施：

1. 展示目录元信息与执行插件分离。元信息只能支持名称、图标占位和兼容性展示，不能据此授权执行后台。
2. 原生插件完整校验放入宿主控制的后台任务，限制并发；首个选中插件优先，其余在可操作后排队。校验通过前不加载该插件代码。
3. 安装、更新、开发重载维持完整包校验；缓存失效与安装代次绑定。不能仅凭 mtime / size 跳过内容校验，也不能把应用签名当作用户插件签名的替代品。
4. 后台按打开、提醒、主动采集、MCP 查询、备份导入等用途准备，使用同一准备 Promise 合并并发请求。
5. 已停用或卸载后保留的数据处理器，在用户备份、导入、恢复时再准备。必须同步改造备份合同，避免延迟加载后导出漏数据。
6. 待办提醒、用户已开启的采集按声明的后台需求启动，不因页面未打开而丢提醒或停止采集。

边界：宿主只提供通用生命周期与调度能力，具体业务状态仍归插件；不能在主程序写死“日历要等待办”等依赖。

验收：安装重型插件不会线性增加首屏时间；未校验插件不能执行；并发打开只准备一次；停用期间的初始化、在途写入和任务正确取消或等待。

### P0：macOS 专项

- 分别测钥匙串等待、凭据解密、签名验证、磁盘读取、WebContents 创建和首次业务渲染，不能把全部延迟归因于系统权限。
- 继续使用异步安全存储，账号相关请求等待凭据就绪，本地工作台不等待登录。
- 核对安装器与运行进程架构；同时核对稳定的应用签名身份。首次系统校验或钥匙串授权与日常启动分别统计，不承诺签名能消除所有启动延迟。
- 实机做 Instruments / Chromium trace，确认 CPU 热点、磁盘等待和主线程阻塞后再改，不默认禁用 GPU 或降低沙箱安全。

## 6. 进程、内存和可扩展架构

### P1：统一任务预算，保留插件隔离

现状：PluginTaskPool 主要限制单个插件并发；一次计算会建立子进程，子进程内部再建 Worker。它提供故障隔离，但频繁的小任务可能承担较大冷启动成本，多个插件的总并发也没有统一预算。

方案：测清进程启动、模块加载、数据复制和实际计算的占比。宿主增加总并发、优先级、队列和取消协议；当前交互优先于后台扫描。达到上限时排队并反馈，替代立即返回“繁忙”。

高频可信解析任务可评估同插件短时复用执行进程，空闲超时释放；不跨不同插件共享可变执行环境。OCR、超大解析等维持独立故障边界。复用前必须测试内存残留、模块状态串扰、崩溃重建与卸载清理。

大图片和表格数据尽量使用可转移二进制或受控资源句柄，减少主进程 ↔ 子进程 ↔ Worker ↔ 页面反复 Base64 / JSON 复制。需要改协议时做版本兼容，资源句柄有所有者、过期与释放规则。

### P1：按内存压力回收，而非只按页面数

现有回收以可回收声明、页面数量和空闲时间为主，不能代表页面实际资源成本。

增加资源等级、最近使用、脏状态和任务状态。已保存的重型后台页面优先释放，轻量页可保留；未保存内容先可靠保存或保持驻留。页面恢复只重建需要的视图。处理睡眠唤醒、系统内存压力和桌面组件独立存活。

### P2：性能友好的模块边界与编码约束

- 宿主负责调度、权限、测量和生命周期；插件负责算法和业务，公共优化不引入业务耦合。
- 状态模块提供 capture / restore / dispose 等明确方法，避免外部模块直接修改内部数组和搬动 DOM。
- 缓存必须写明 key、上限、失效、所有者与释放时机；Promise 缓存失败后必须可重试。
- 异步请求统一带操作代次或取消信号；页面隐藏、切换、更新、卸载后不再接收旧结果。
- 主进程新增同步 IO 必须说明必要性；有界小操作允许保留，批量扫描、解码、哈希与复杂序列化不进入交互路径。
- 大列表不在 render 内重复全量排序、深拷贝和查找；共享样式与控件复用，避免多个初始化器重复绑定事件。

## 7. 视觉反馈与过渡

性能验收以真实完成为准，反馈优化独立实施：按钮立即显示处理中；内容区保持尺寸，避免空白和布局跳动；加载失败提供重试，不无限显示转圈。轻量浮层使用约 100–160ms 的透明度或位移过渡，支持减少动态效果；避免大面积持续模糊、阴影动画及循环装饰动画。

隐藏页面停止非必要动画和绘制；提醒与主动采集维持业务需要，不把省电等同于暂停全部后台功能。禁用减少动态效果与动画完成均不得决定业务操作是否执行。

建议每批交付固定包含：改动前后同机 P50/P95、数据规模、代码与包版本、功能回归结果、CPU/内存代价和未解决事项。无显著收益的高复杂度改动可以撤回。

## 9. CI 与发布门禁

既有测试保留，并新增小数据、大数据、取消、切换、停用、升级及异常恢复的性能场景。真实桌面测量使用正式打包产物；CI 虚拟机用于回归趋势，不作为用户设备 SLA 的替代。

每个关键场景在同类环境比较基线。建议 P95 相对恶化超过 15% 且超过预设绝对容差时报警，复跑确认后阻止发布；功能失败、数据丢失、签名绕过、任务泄漏直接阻止发布。所有平台保留性能产物，记录任务重跑，不能仅靠放宽等待超时让检查变绿。

实施前先验证热插拔、备份完整性、提醒补发和用户内容保护；实施后检查跨架构兼容。稳定版可先发布小范围验证，但不自动上传用户内容或开启遥测。

## 11. 启动优化实施进展

2026-11-21 保留的实现：后台初始化请求合并、按需准备及受控分批接口；初始化期间卸载会等待并释放。备份、数据导入、团队配置和启动 MCP 前补齐处理器，启动恢复日志仍优先恢复。主程序沿用原有后台准备顺序，首屏后再全量初始化的实验调度已撤回，不计入当前启动收益。

公共 SDK 资源增加 12MiB 上限的共享缓存；正式包缓存随宿主发布的只读文件，开发模式按文件身份、大小及修改时间失效，用户插件和临时预览仍读取实际文件。无目录变化的状态更新不再重建插件栏与二级导航，普通切换只调整选中状态，主题未变化不重复应用。

早期实验包的一次 Windows x64 隔离记录：首插件页面就绪 1326ms、宿主 HTML 就绪 1408ms；40 次相同状态更新约 3ms，导航节点保持；缓存复用 20 项公共资源，占 585113 字节。该包早于调度撤回，不代表最终版本的启动成绩；指标仍是页面载入，不是业务可操作 P95，也不与开发模式数据计算加速比。

仍待实施：完整签名校验的后台调度、业务 ready 合同、Mac 实机基线、真正按后台用途的永久惰性加载、大数据交互和任务总预算。当前不减少签名校验范围，也不宣称已达到整个方案的最终目标。

开发模式退化反馈后的纠正：协议资源路径检查恢复为单次同步校验，撤回逐段异步文件检查；公共 SDK 在开发模式也缓存，依据文件身份、大小与修改时间失效；公共控件脚本并行请求、保序执行。撤回主程序“首屏后再全量初始化后台”的调度调整，恢复原先准备顺序；通用的分批准备及并发合并接口仍保留供受控场景使用，不能把它算作当前启动收益。页面缓存容量由 4 调整为 6，避免默认五插件切换时反复重建可回收页面。新增回归检查实际 WebContents 身份是否复用，以及公共资源编辑后能否立即读到新内容。

本机对照中已复现旧策略会回收便签页，第二轮打开约 407ms；修正后默认五插件第二轮均复用原页面。但 Windows 首次打开的结果仍有波动，不能据此宣称 Mac 首开两秒问题已经解决。开发模式中超过 800ms 的页面打开会输出耗时分段，区分页面载入、后台准备和页面复用状态，供实际慢环境定位。
